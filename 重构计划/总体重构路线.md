## 一、总目标与路线原则

### 1.1 目标形态

采用源计划的路线 C：**把账号、会话、请求编排和运行状态迁移到 App QuickJS，把传输、算法和 PoW/WASM 执行能力沉淀为 Native JSAPI 库。**

最终主链路为：

```text
App UI
  → DsRuntime（唯一业务入口）
  → JS 账号池 / 会话 / 上传 / completion / HIF / 设备身份
  → Native Transport / Crypto / PoW
  → DeepSeek 原生接口
```

最终 App 运行路径不再依赖独立 `ds-free-api` 进程、固定本地服务端口、OpenAI/Anthropic 兼容服务、Axum/Admin/JWT 中间层或 curl 文件轮询 SSE。

### 1.2 固定原则

1. **先验证宿主，再迁移业务**：阶段 0 是路线 C 的硬门槛，只有真实设备验证通过才进入后续阶段。
2. **按职责拆分，不逐文件翻译**：先定义状态模型和接口，再拆解 `accounts.rs`、`client.rs`、`completions.rs` 等业务。
3. **保留已知行为，减少同时变化的因素**：初期保留源计划指定的传输行为和现有 PoW 执行方式，不同时替换宿主、WASM runtime、算法和业务编排。
4. **Native 不持有业务状态**：账号、session 策略、禁言、限流、重试、HIF 策略、设备身份映射和配置真源均归 JS。
5. **先替代并验证，最后删除**：旧链路保留到正式切换及观察验收完成，最终清理单独放行。
6. **以验收记录推进，不以文件数量推进**：写出 `.so`、新增模块或完成打包都不等同于阶段通过。
7. **保持业务体验范围**：仅改造完成迁移所需的服务入口和状态连接，不把 UI 重设计或无关功能开发纳入本路线。

## 二、总体阶段图与依赖

沿用源计划的阶段 0—5 编号；阶段 5 内部细分切换、观察、退役，不另起一套阶段编号。

```text
执行前：确认行为基线、接口约定、验收样本、配置备份和回滚入口
  ↓
阶段 0：最小 JSAPI / ABI / 异步生命周期验证                    [G0]
  ↓
阶段 1：通用 Native Transport                              [G1]
  ↓
阶段 2：现有 PoW/WASM 执行能力库化                           [G2]
  ↓
阶段 3：JS 业务、配置、生命周期迁移及非默认入口集成              [G3]
  ↓
阶段 4：真实浏览器 device capture 独立接入与身份闭环             [G4]
  ↓
阶段 5A：正式切换默认调用路径，保留兼容开关                      [G5A]
  ↓
阶段 5B：真机观察、升级回归、回滚演练                           [G5B]
  ↓
阶段 5C：移除旧进程部署链路及兼容服务依赖                       [G5C]
```

**Crypto 支线**：阶段 0 通过后，按实际依赖评估纯算法库；在阶段 3 或阶段 4 的消费者接入前完成所需能力及固定样本验证。优先使用真实浏览器采集方案，不因原计划列出了 Crypto 库就提前重写整条 mint 链路。

### 2.1 依赖与推进规则

| 路线单元 | 前置条件 | 放行结果 |
|---|---|---|
| 阶段 0 | SDK、固件、打包和导入方式有明确核验路径 | 证明自定义 Native 模块在目标宿主内可靠运行 |
| 阶段 1 | G0 通过 | 传输可独立验证，生命周期契约成立 |
| 阶段 2 | G0、G1 通过后按主线推进 | PoW 结果与既有实现一致，运行时资源可控 |
| 阶段 3 | G1、G2 通过；所需 Crypto 能力就绪 | 新业务链在非默认入口具备完整功能和清理语义 |
| 阶段 4 | 设备身份接口、持久化和业务消费路径就绪 | 采集、保存、登录、重启复用形成一致闭环 |
| 阶段 5A | G3、G4 及跨模块验收通过 | 新路径成为默认，旧路径仍具备回滚用途 |
| 阶段 5B | 默认切换完成且记录可观测 | 完成约定观察场景并验证回滚可用 |
| 阶段 5C | G5B 通过，删除范围及版本回退方式确认 | 最终运行包脱离旧进程和中间兼容服务 |

阶段依赖描述的是推进顺序，不是本轮启动开发或分派任务的指令。某一门槛缺少证据时，保持该门槛为待验证状态，不跨阶段宣告完成。

### 2.2 源计划中的口径统一

以下是本路线为后续实施提出的统一约定，不冒充已经冻结的接口：

- **默认切换时间**：源计划第 11 节写“阶段 3 才切换”，最终建议则将切换放在 device capture 之后。本路线把阶段 3 解释为最早具备新入口和兼容开关的阶段，正式默认切换放在阶段 4 验收之后的 5A，以最终建议的完整顺序为准。
- **Transport 接口**：源计划同时出现 `requestStream/data` 和 `openStream/chunk`。阶段 1 开始时统一命名、事件归属、取消与终止语义，只保留一套正式契约。
- **Runtime 退出接口**：源计划同时出现 `stop()` 与 `shutdown()`。阶段 3 明确唯一对外退出语义及内部清理顺序，避免消费者各用一套。
- **Probe 接口**：`asyncEcho()` 与任务书的异步 `echo()` 指同类验证能力，阶段 0 固定一种命名；验收关注 Promise 行为而非名称。
- **PoW JS 桥接模块**：源计划目标目录包含 `ds-pow.js`，阶段 3 顺序未单独列出。本路线将其明确纳入挑战获取、target 选择和 Native solver 调度职责。
- **Crypto 排期**：源计划定义了库边界但未单列阶段，本路线按消费者依赖插入支线，不扩大为新的全量算法重写工程。

## 三、目标职责与迁移范围

### 3.1 分层边界

| 层级 | 拟承担职责 | 明确排除的职责 |
|---|---|---|
| UI | 展示业务状态，提交用户意图，订阅业务事件 | 直接操作 Native transport、拼装 PoW、维护账号占用 |
| `DsRuntime` | 配置装配、启动状态、业务入口、请求归属、取消与退出 | 重复建立底层传输栈，承担全部细粒度业务实现 |
| JS 业务模块 | 账号、登录、会话、历史、上传、PoW 调度、completion/edit、SSE 语义、HIF、设备身份和错误策略 | 直接实现 TLS 或阻塞主线程的网络/计算 |
| Native Transport | HTTP/HTTPS、TLS/HTTP2、Cookie Jar、代理、超时、重定向、原始字节流、取消和通用错误 | 账号池、DeepSeek 专用 endpoint、业务 token 管理、session 策略、禁言或重试决策 |
| Native Crypto | 约定的 AES/RSA/DES/MD5/SHA/Base64 等算法能力 | deviceprofile 业务 payload、登录流程、设备身份状态或验证码业务 |
| Native PoW | 接收 WASM 和计算输入、执行求解、返回兼容结果、管理计算资源 | 下载挑战、选择业务 target、持有账号、决定重试或发起业务请求 |
| App storage | 账号、设置、代理、HIF 配置、设备凭据的运行时真源 | 与 TOML 双主写入，或交由 Native 维护业务配置 |

边界补充：Transport 可以传送业务 header/body，但将其视为不透明数据；可以用通用 client/context 句柄隔离 Cookie 和代理，但不识别账号对象。PoW 可以接收 `targetPath`、`signature` 并返回兼容输出，但操作类型、target 选择以及向请求附加 header 的责任留在 JS。

### 3.2 按职责迁移的模块映射

| 源计划涉及部分 | 目标去向 | 处理原则 |
|---|---|---|
| `ds_core/accounts.rs` | `account-state.js`、`account-pool.js` | 保留一账号一并发、状态与恢复语义 |
| `ds_core/client.rs` | Native Transport + `ds-client.js` | 传输构建与业务 API 调用拆开 |
| `ds_core/completions.rs` | `ds-session.js`、`ds-upload.js`、`ds-completion.js`、`ds-runtime.js` | 按请求生命周期和资源责任拆分 |
| `ds_core/pow.rs` | Native PoW + `ds-pow.js` | 首期保持算法/执行行为，JS 负责业务调度 |
| `ds_core/hif.rs` | `ds-hif.js` | 保留适用请求、有效期及失败处理语义 |
| `fingerprint.rs`、`mint.rs`、`device_bootstrap.rs` | `ds-device.js` + device capture；按需调用 Crypto | 优先真实浏览器采集，区分采集、存储与请求使用 |
| `server/device_capture.rs` 中可复用的页面/交互设计 | App 可用的采集页面与回传桥接 | 复用能力，不把 Axum 服务一并搬入 App |
| `config.rs` 的必要业务字段 | App 配置对象与 storage | TOML 仅作一次性兼容导入来源 |
| OpenAI/Anthropic adapter、Axum/Admin/JWT 等 | 最终 App 目标架构不迁入 | 旧路径仍需使用的部分保留至阶段 5C 再处理 |
| App 现有进程启动、健康检查、后端 blob、curl 轮询 | 阶段 5C 退役范围 | 新路径验收和回滚准备先于清理 |

本表是目标归属，不是本轮文件修改清单；源计划中的代码行数估算不作为拆分单位或完成率。

## 四、分阶段总体路线

### 阶段 0：证明 Native JSAPI 在目标设备上成立

**目标**：先回答“目标 App 宿主是否可靠支持私有 Native 模块”，暂不讨论业务迁移成效。

**拟开展事项**：

- 核对 SDK/头文件、`jqutil_dist`、固件、架构和依赖装载条件。
- 以 `app/libs/arm64/libjsapi_ds_probe.so` 为最小探针，验证 amr 打包、PMS 解包和 JS import。
- 验证同步 `version()`、异步 echo、事件回调，以及重复加载、退出和升级后的行为。
- 明确线程、Promise、回调引用和 QuickJS 生命周期之间的所有权约束。

**拟交付物**：最小探针、环境与 ABI 核验记录、构建/安装/运行记录、已知限制清单。

**G0 验收门槛**：真实设备能够加载模块；同步返回、Promise 和事件回调稳定；App 退出或库更新后无失效回调访问。SDK/ABI 信息不齐时仅补齐环境诊断，不猜测未知 ABI。

**边界与回滚**：不加入 TLS、HTTP、PoW 或 DeepSeek 业务；保留现有 App 和后端调用链，撤去探针即可回到原基线。

### 阶段 1：建立纯通用 Native Transport

**目标**：用进程内异步字节流代替未来新路径中的额外 curl 进程和文件轮询。

**拟开展事项**：

- 以源计划指定的 `wreq`、Chrome136 emulation、HTTP/2、Cookie、代理、超时和重定向行为为迁移基线，实施时核对当前代码。
- 统一普通请求、流式请求、headers、chunk、end/error、cancel 的接口契约及请求标识。
- 明确流事件顺序、终止事件唯一性、取消幂等、队列/缓存上限和背压处理。
- 为多身份请求提供通用传输上下文隔离，防止共享 Cookie Jar 或代理设置相互污染。
- 明确回调投递到 QuickJS 的方式；Transport 返回原始字节，不解析业务 SSE 事件。

**拟交付物**：传输库、JS 桥接契约、mock server 验收用例及记录、资源生命周期说明。

**G1 验收门槛**：GET、POST JSON、Set-Cookie/回传、302、401/429、分片流、跨 chunk UTF-8、超时、取消、重复请求、销毁场景全部有证据；401/429 作为可观察 HTTP 结果交给业务层决策。TLS/HTTP2 与代理行为须另有对应验证，普通 mock 请求成功不等同于传输特征已经对齐。

**边界与回滚**：不加入登录、账号、业务 token 管理、session、PoW、禁言或业务重试；不切换默认入口。回滚只撤销新传输接入，旧路径仍工作。

### 阶段 2：库化现有 PoW 能力，先保证一致性

**目标**：让 App 调用现有求解能力，而非同时重写算法和运行时。

**拟开展事项**：

- 首期以现有 Rust PowSolver/Wasmtime 行为为基线，接收下载完成的 WASM 字节和显式计算参数。
- 由 JS 管理 WASM 获取、挑战获取、有效期检查和业务 target；Native 只负责求解与通用资源管理。
- 约定并发限制、过期任务处理、取消/退出语义，以及 runtime 初始化和复用范围。
- 用固定样本对比输出，并记录内存、耗时、重复调用及 App 退出时的资源表现。

**拟交付物**：PoW 库、固定回归样本、与旧实现的对照结果、运行时兼容性及资源记录。

**G2 验收门槛**：相同有效输入的 `answer/header` 与现有实现一致；异常、过期、重复和并发调用可控；计算不阻塞 QuickJS 主线程；退出前有明确的任务终止和资源回收路径。

**边界与回滚**：不在此阶段改用 Wasmi 或专用算法；不把账号和网络策略塞进 solver；验证入口回退到既有实现。

### 阶段 3：迁移 JS 业务、配置和运行生命周期

**目标**：通过稳定业务入口组合 Native 能力，在默认路径不变的前提下完成新业务链验证。

**建议内部顺序**：

1. **基础契约**：`ds-types.js`、`ds-errors.js`，明确业务请求、事件、错误和取消模型。
2. **账号状态与占用**：`account-state.js`、`account-pool.js`，实现原子 acquire、幂等 release、禁言/限流/恢复状态。
3. **身份与请求基础**：`ds-client.js`，先固定 `ds-hif.js`、`ds-device.js` 的消费契约；使用已保存的有效凭据，不同步替换采集实现。
4. **业务链路**：`ds-session.js` → `ds-pow.js` → `ds-upload.js` → `ds-completion.js`；按原有策略连接登录、历史处理、会话、上传、completion/edit 和 SSE。
5. **策略补齐**：完成 HIF 适用范围、账号恢复、设备凭据消费、云端会话同步等完整业务能力。
6. **配置与总运行时**：`ds-runtime.js` 装配 storage、传输和计算库，实现启动、ready、取消、退出及统一状态通知。
7. **非默认集成**：UI 通过业务服务入口使用新链路；保留旧入口与兼容开关，避免同一请求同时发到新旧链路。

**关键链路**：

```text
原子占用账号
  → 按现行策略创建/复用 session，处理历史
  → 按需上传文件并使用上传专属 PoW target
  → 创建 completion/edit 所需挑战并求解
  → 发起请求、处理 ready、增量解析 SSE
  → 正常完成或取消/异常
  → 终止关联传输、履行 session 清理责任、释放账号
```

历史拆分、创建/复用 session 等内部先后关系由执行者对当前代码和基线用例确认；这里表达总体职责，不以摘要替代现有准确行为。

**配置与生命周期要求**：

- 首次升级兼容导入：`config.toml → JS 配置对象 → storage`；导入有版本/完成标记、备份和失败回退，不在每次启动时覆盖 App 配置。
- 目标运行时以 storage 为唯一业务配置真源，Native 不持久化账号配置。
- 启动状态覆盖 `created → starting → transport_ready → pow_ready → accounts_loading → ready`；账号初始化尚未结束时不得报告业务 ready。
- 停止顺序为停止接收新任务、取消/等待活跃任务、结束回调投递、释放业务资源、销毁 Native runtime，最终进入 stopped。
- 页面退出清理其所属请求；App 级 Runtime 的销毁归属在契约中明确，避免页面重进重复初始化。
- 初始化失败也有可观察错误和清理路径；重复 start/cancel/stop 的处理须确定。

**拟交付物**：JS 模块、业务接口说明、配置迁移策略、新旧行为对照矩阵、生命周期与异常路径验证记录。

**G3 验收门槛**：登录/切号、发送/取消、多轮、图片/文件、思考/搜索、重试/编辑、云端会话及账号状态完整；账号占用、资源清理、PoW target、HIF、SSE 和配置迁移满足第五节不变量。业务通过验证不代表默认切换已经完成。

**边界与回滚**：不整体翻译大型 Rust 文件，不顺带改造页面设计，不同时替换 mint；停止新 Runtime 后回到旧入口。保留迁移前配置备份，并明确新配置/新增数据的兼容处理，避免回退时静默丢失。

### 阶段 4：独立完成 device capture 与身份一致性闭环

**目标**：在业务链稳定后，单独替换设备凭据获取方式，隔离业务迁移与身份迁移的变量。

**拟开展事项**：

- 优先复用现有 device capture 设计，由 WPE WebKit 运行官方 `fp.min.js`，获取成对的 `device_id` 与 `smidV2`。
- 确定采集页装载和向 App 回传的桥接方式；最终方案不重新引入完整 Axum 服务或固定后端端口依赖。
- 将采集结果提交给 JS 业务层，由其协调内存账号、Cookie Jar、storage 更新，并保证重启后继续使用相同凭据。
- 关联 UA、client platform、代理与 TLS profile 的身份上下文，避免不同请求路径独立生成或混用。
- 采集失败时保持上一个一致的凭据版本，明确提示和恢复流程，避免半更新。

**拟交付物**：采集与回传方案、身份上下文契约、持久化/恢复流程、登录/重启/多账号隔离验证记录。

**G4 验收门槛**：采集值、登录使用值、Cookie、内存和持久化值一致；重启、失败恢复和多账号使用不串值；不因普通启动反复生成新身份。

**边界与回滚**：不把 Crypto 库变成业务 mint 库，不将移植完成等同于风控问题已经解决。必要的 Native Crypto + JS payload 方案须单独评估；全量纯 JS payload 排在更后，不与主线同步展开。回滚采集入口时保留完整一致的旧凭据快照。

### 阶段 5：默认切换、观察、旧架构退役

#### 5A：正式默认切换

- G3、G4 及跨模块回归通过后，新 Runtime 成为默认业务入口。
- 保留明确的兼容开关和旧版本回退包；切换前结束旧链路任务，新旧路径不同时占用同一账号。
- 明确配置转换、登录状态、设备凭据和用户新产生数据在回滚中的处理。
- **G5A**：用户核心功能经新默认入口完成，退出和取消正常，回到旧入口的路径可用。

#### 5B：真机观察和升级回归

- 观察时长及门槛在切换前约定，不在缺乏设备数据时臆定固定天数。
- 至少覆盖重复启动、页面退出重进、断网、长流取消、账号禁言/限流、设备重启和 App 升级。
- 关注请求/stream/PoW 任务数、busy 账号归零、session 清理、内存趋势、错误分类及身份一致性；记录脱敏，避免输出凭据和 token。
- 演练功能开关回退与版本回退，说明各自的数据兼容边界。
- **G5B**：约定观察场景通过，无未解释的关键资源遗留，回滚记录完整，关键功能与状态回归达标。

#### 5C：最终清理和退役

- 核对所有调用方已迁移后，按依赖清理 App 中的旧进程启动、`fuser/pkill`、`nohup`、端口探测、`/health` 轮询和僵尸进程处理。
- 移除旧后端 blob 分发、运行时 TOML IPC、curl 文件轮询；根据导入兼容承诺决定 TOML 导入工具的保留期限。
- 在 App 迁移交付范围内退役不再需要的 OpenAI/Anthropic adapter、Axum/Admin/JWT 等依赖。独立后端源码是否整目录删除，另行核对其他使用方后决定，不因 App 切换成功就扩大删除范围。
- **G5C**：最终 App 在不启动旧进程、不依赖固定后端端口和旧 key 的条件下通过完整验收；构建/打包依赖已解除。
- **回滚边界**：清理前可用兼容开关；清理后依赖已留存的上一版本包及配置/数据兼容方案，不能再把已删除实现视为在线开关回退路径。

## 五、贯穿全程的验收不变量

以下要求进入相关阶段验收，不留到最终阶段集中补测。所有验证活动均属于未来实施工作。

| 编号 | 不变量 | 最低验收覆盖 |
|---|---|---|
| I1 | 一个账号同一时刻最多服务一个活跃请求 | acquire 原子完成；busy 账号不被重复获取；并发进入和异常退出后占用正确 |
| I2 | 每个请求都有唯一资源清理责任 | 正常、取消、断网、上传/PoW/completion 失败、禁言、空流、解析异常、页面销毁均释放账号并终止传输 |
| I3 | session 策略保留，清理责任显式 | 新建 session 的归属和清理有记录；复用或云端保留会话按既有策略处理，不以统一删除破坏同步功能 |
| I4 | PoW target 由业务操作显式确定 | completion 使用 `/api/v0/chat/completion`；upload 使用 `/api/v0/file/upload_file`；edit_message 对照现有定义核实 |
| I5 | 设备身份是完整上下文 | device_id、smidV2、Cookie、UA、client platform、代理、TLS profile 一致；重启和账号切换不漂移、不串用 |
| I6 | 错误分类决定有限且明确的恢复策略 | 保留 NoAccounts、Overloaded、RateLimited、Rejected、ProofOfWorkFailed、ProviderError、StreamError、Muted、Unauthorized、CaptchaRequired 等语义 |
| I7 | SSE 正确处理字节与事件边界 | CRLF/LF、多行 data、事件跨 chunk、UTF-8 跨 chunk、空流、中断、`[DONE]` 及尾随 usage/ds_title/ds_session_id |
| I8 | HIF 按适用条件发送 | 适用/不适用请求、有效期与失败恢复对照既有行为；Transport 不自行注入 HIF |
| I9 | 配置只有一个业务真源 | storage 主导；TOML 导入不反复覆盖；Native 不读取或持久化账号配置；迁移失败可恢复 |
| I10 | Native 生命周期先收任务再销毁 | 停止 stream/PoW、处理取消和晚到回调后释放 runtime；无失效 JS 引用访问 |
| I11 | QuickJS 主线程保持响应 | 网络、重计算及阻塞磁盘路径不落在主线程；背压、缓存与并发边界有验证 |
| I12 | 新旧路径隔离 | 同一用户请求仅执行一次；回滚前结束另一条路径；保留数据与凭据一致性 |

### 5.1 错误策略底线

- 所有账号忙：可等待或有限重试，不能误记为上游限流。
- 上游限流：进入明确冷却，不快速连续换号撞请求。
- 禁言：标记账号状态，不把禁言包装成临时网络错误自动重试。
- 输入超长或请求错误：直接反馈，不换账号、不自动重试。
- PoW 失败：区分参数、有效期和执行错误，按显式策略处理，不无限循环。
- 网络断开：先释放资源，由用户或已定义的有限恢复策略决定下一步。
- token 失效：最多单次受控登录恢复，仍失败则反馈。
- 验证码需求：保持独立错误/交互语义，不归入通用网络重试。

### 5.2 最终完成定义

**功能完整 + 架构边界成立 + 资源生命周期稳定 + 配置/身份一致 + 升级/回滚可验证 + 旧运行链路退出**，六项共同满足才视为路线 C 完成。仅“可以发出一条消息”不构成最终验收。
