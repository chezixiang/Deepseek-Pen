# ds-free-api 向 App 端迁移分析报告

**日期：2026 年 9 月 27 日**  
**目标路线：路线 C——传输/密码学/WASM 库下沉，业务逻辑迁移到 App 端**  
**实施主体：Astra**  
**本报告性质：方案分析与实施任务说明，不修改任何文件**

---

## 1. 总结结论

建议采用路线 C，但不建议把当前 `ds-free-api` 原样搬进 App，也不建议用 C++ 重新实现全部业务。

推荐目标结构：

```text
App QuickJS 业务层
├── 账号池与账号状态
├── 登录、会话、文件上传
├── PoW 调度
├── HIF token 管理
├── DeepSeek 请求编排
├── SSE 业务事件解析
├── 禁言、限流、重试、账号冷却
└── App UI / storage

Native JSAPI 库层
├── Chrome 风格 TLS/HTTP2 传输
├── Cookie Jar / 代理 / 超时
├── 增量 SSE 字节流
├── AES / RSA / DES / MD5 / SHA
└── WASM 或 PoW 执行器
```

迁移后的核心原则：

1. **App 端只保留 DeepSeek 原生业务链路。**
2. **删除 OpenAI 适配器、Anthropic 适配器、Axum HTTP Server、Admin/JWT 等中间服务逻辑。**
3. **TLS、HTTP、加密、WASM 仅作为库，不允许混入账号、会话、禁言、重试等业务状态。**
4. **App 端的行为必须继续保持当前后端行为：**
   - 账号池一账号一并发；
   - 每次请求按当前会话策略创建或复用 DeepSeek session；
   - 文件上传与 completion 使用正确 PoW target；
   - 限流和禁言不进行无意义换号重试；
   - SSE 流中断时释放账号、清理 session；
   - device_id、smidV2、Cookie、代理和 UA 保持同一身份链；
   - HIF token 只在适用请求中发送。

## 3. 路线 C 的目标架构

## 3.1 Native 库边界

Native 层只处理通用能力，不感知 DeepSeek 业务。

### `libjsapi_ds_transport.so`

职责：

```text
request()
requestStream()
cancel()
setProxy()
clearCookies()
getCookies()
```

输入：

```js
{
  method: "POST",
  url: "...",
  headers: {...},
  body: Uint8Array 或 string,
  timeoutMs: 15000,
  stream: true
}
```

输出：

普通请求：

```js
{
  status: 200,
  headers: {...},
  body: Uint8Array
}
```

流式请求：

```js
{
  streamId: "stream-xxx"
}
```

通过事件返回：

```js
dsTransport.on("data", callback)
dsTransport.on("headers", callback)
dsTransport.on("end", callback)
dsTransport.on("error", callback)
```

Native 层不得出现以下概念：

```text
account
session_id
mute
rate_limit
DeepSeek
create_session
completion
device_id
model_type
```

### `libjsapi_ds_crypto.so`

只暴露算法：

```js
md5(data)
sha256(data)
aesCbcEncrypt(key, iv, data, padding)
rsaPkcs1v15Encrypt(publicKey, data)
desEcbZeroPadEncrypt(key, data)
base64Encode(data)
base64Decode(data)
```

该库不负责：

- deviceprofile payload；
- smid 生成；
- 登录请求；
- DeepSeek header；
- captcha；
- 账号配置。

### `libjsapi_ds_pow.so`

只暴露：

```js
solvePow({
  wasmBytes,
  algorithm,
  challenge,
  salt,
  expireAt,
  difficulty,
  targetPath,
  signature
})
```

输出：

```js
{
  algorithm,
  challenge,
  salt,
  answer,
  signature,
  targetPath,
  header
}
```

库层不得知道：

```text
哪个账号在使用 PoW
这是 completion 还是 upload
是否要重试
账号是否被禁言
```

## 3.2 App 业务层

App 业务层负责完整的 DeepSeek 逻辑。

### 账号池

从 `accounts.rs` 迁移：

```text
AccountPool
├── account list
├── token
├── busy
├── state
├── muteUntil
├── cooldownUntil
├── hourly quota
├── lastError
└── recovery state
```

必须保持的核心不变量：

```text
一个账号同一时刻最多服务一个活跃请求
```

账号获取必须是原子操作：

```js
const guard = await accountPool.acquire()
try {
  return await runChat(guard.account)
} finally {
  guard.release()
}
```

不能出现：

```js
const account = accountPool.findIdle()
await somethingAsync()
account.busy = true
```

否则并发下会发生同一账号重复占用。

### 会话编排

当前真实流程必须保持：

```text
v0_chat
→ acquire account
→ 判断 session reuse
→ create_session 或复用 session
→ split history
→ upload files
→ create PoW challenge
→ solve PoW
→ completion / edit_message
→ 解析 ready
→ 解析 SSE
→ 完成或中断
→ 清理 session
→ release account
```

所有退出路径都必须释放资源：

```text
正常结束
用户取消
网络断开
PoW 失败
上传失败
completion 返回错误
上游返回禁言
SSE 空流
解析异常
App 页面销毁
```

### 错误分类

App 端必须保留当前错误语义，不要把所有错误归一为网络失败：

```text
NoAccounts
Overloaded
RateLimited
Rejected
ProofOfWorkFailed
ProviderError
StreamError
Muted
Unauthorized
CaptchaRequired
```

尤其要保留以下区别：

| 错误 | 是否换账号 | 是否自动重试 |
|---|---|---|
| 所有账号忙 | 可以等待其他账号 | 可以有限重试 |
| 上游 rate limited | 不应连续换号撞请求 | 不自动快速重试 |
| user is muted | 标记账号禁言 | 不重试 |
| 输入超长 | 不换账号 | 不重试 |
| PoW 失败 | 标记请求/账号异常 | 依策略处理 |
| 网络断开 | 释放资源 | 可由用户重试 |
| 401 token 失效 | 重新登录账号 | 单次受控恢复 |

## 4. 传输层迁移策略

当前后端的传输层核心在：

```text
ds-free-api/src/ds_core/client.rs
```

其中 `base_http_builder()` 使用：

```text
wreq
Chrome136 emulation
Cookie Jar
代理
连接超时
重定向限制
```

这部分是路线 C 最重要的保留对象。

## 4.1 不能直接用 App 的 `$falcon.jsapi.http` 替代

当前 App 的 `$falcon.jsapi.http` 存在两个问题：

1. 没有可靠的增量回调；
2. 当前流式回复依赖 `curl -N` 写文件，再由 JS 每 200ms 轮询。

目前 `ds.js` 中的流式方案是：

```text
execShell(curl -N ...)
→ 输出文件
→ QuickJS 轮询文件
→ parseSse()
```

这套方式可以工作，但存在：

- 额外进程；
- 双重 HTTP 栈；
- 文件 IO；
- 取消不及时；
- 错误状态不完整；
- 长连接生命周期复杂；
- 进程杀错风险；
- 后端与 App 日志分离。

因此路线 C 的主要收益之一，就是把流式请求改成 Native transport 事件回调。

## 4.2 Native transport 的推荐接口

不要在 JSAPI 中暴露 DeepSeek 专用方法：

```js
// 不推荐
deepseekLogin()
deepseekCompletion()
deepseekUpload()
```

推荐通用请求接口：

```js
const request = await DsTransport.request({
  method: "POST",
  url,
  headers,
  body,
  timeoutMs
})
```

流式：

```js
const stream = await DsTransport.openStream({
  method: "POST",
  url,
  headers,
  body,
  timeoutMs
})

stream.on("chunk", onChunk)
stream.on("end", onEnd)
stream.on("error", onError)
```

这样可以保证：

- Transport 可以独立测试；
- 业务逻辑在 JS 中可观察；
- 将来更换 DeepSeek 接口时不需要重新编译 Native 库；
- TLS 库不携带业务；
- 便于 Astra 分阶段实现。

## 5. PoW 迁移方案

PoW 是路线 C 的一个硬门槛。

当前实现：

```text
ds-free-api/src/ds_core/pow.rs
```

特点：

- 下载 DeepSeek WASM；
- 动态探测导出函数；
- 使用 Wasmtime；
- 调用 `wasm_solve`；
- 生成 `X-Ds-Pow-Response`。

设备当前 QuickJS/框架中没有可靠的 WebAssembly 能力，因此不能直接把 `pow.rs` 翻译为 JS。

## 5.1 推荐顺序

第一阶段不要重写 PoW 算法，先把现有 WASM 执行能力库化：

```text
Rust PowSolver
→ libjsapi_ds_pow.so
→ JS solvePow()
```

这样能先验证：

- Rust runtime 能否嵌入 JSAPI `.so`；
- tokio/wasmtime 是否能在 App 进程内工作；
- 内存占用；
- 多次并发调用；
- App 退出时 runtime 是否安全回收。

## 5.2 后续缩小运行时

当前 `wasmtime + cranelift` 是体积和编译复杂度最大的依赖之一。后续可以评估：

```text
Wasmtime
→ Wasmi
→ 专用 DeepSeekHashV1 实现
```

但不能一开始就同时改动：

- 宿主；
- WASM runtime；
- PoW 算法；
- 请求编排。

否则出现问题时无法定位是 ABI、runtime、算法还是业务问题。

建议顺序：

```text
阶段 1：原样 Wasmtime 库化
阶段 2：加入 PoW 回归样本
阶段 3：评估 Wasmi
阶段 4：对比 answer/header 完全一致
阶段 5：再考虑缩小 runtime
```

## 6. 设备身份与 mint 迁移

当前 `mint.rs` 存在明显的维护和风控风险：

- payload 中存在大量静态指纹；
- 多账号可能在同一时间窗口批量 mint；
- 设备指纹与请求链的统一性较弱；
- mint 链路与主请求链的代理/TLS 配置曾存在脱节；
- 真浏览器辅助页已经存在于 `server/device_capture.rs`。

因此，迁移时不应优先把纯 Rust mint 原样搬到 JS。

### 推荐优先级

```text
第一选择：
App → 本地 WPE WebKit device capture 页面
    → 官方 fp.min.js
    → 获取真实 device_id + smidV2
    → 回传 App 业务层

第二选择：
Native crypto 库 + JS 构造 payload

第三选择：
纯 JS 实现完整数美 payload
```

第一种方案的优点：

- 已有代码基础；
- 真实浏览器采集设备特征；
- 不需要在 QuickJS 中重新实现 AES/RSA/DES 全链路；
- 减少静态 payload 的重复特征；
- 与当前 `device_capture.rs` 设计一致。

### device_id / smidV2 不变量

必须始终满足：

```text
一个账号使用的 device_id 与登录时 Cookie 中的 smidV2 配对
```

运行时 mint 后必须：

```text
更新内存账号
更新 Cookie Jar
持久化账号凭据
重启后继续使用同一凭据
```

不能出现：

```text
device_id 已更新
smidV2 仍是旧值
配置文件未回写
下次启动重新 mint 新 device_id
```

## 7. 配置与生命周期改造

当前 App 的进程式架构依赖：

```text
写 config.toml
→ 杀旧进程
→ 启动 ds-free-api
→ 轮询 /health
→ 判断 ready
```

路线 C 后应改成：

```text
加载 App storage
→ 初始化 Native transport
→ 初始化 Pow runtime
→ 创建 DsRuntime
→ 加载账号
→ 异步初始化账号池
→ 更新 App 状态
```

推荐生命周期：

```js
await dsRuntime.start()
await dsRuntime.loadConfig()
await dsRuntime.initializeAccounts()

// 页面使用
await dsRuntime.chat(...)

// 页面销毁
await dsRuntime.cancelAll()
await dsRuntime.stop()
```

### 生命周期状态

```text
created
↓
starting
↓
transport_ready
↓
pow_ready
↓
accounts_loading
↓
ready
↓
stopping
↓
stopped
```

必须避免：

```text
UI 认为 ready，但账号池尚未初始化
UI 页面重进导致重复初始化
旧 stream 没取消，新的 stream 又开始
Native runtime 已销毁但 JS 回调仍在执行
```

### 配置迁移

不要继续把 TOML 当成 App 与后端之间的 IPC。

推荐：

```text
storage:
  accounts
  deepseek settings
  proxy settings
  hif settings
  device credentials
```

TOML 只保留兼容导入能力：

```text
首次升级：
config.toml → JS 配置对象 → storage
```

迁移完成后：

```text
App storage 为主
config.toml 不再作为运行时真源
```

## 9. 实施中的核心不变量

Astra 实现时必须把下面这些作为固定验收条件，而不是靠每个模块自行猜测。

### 9.1 账号并发

```text
busy=true 的账号不能再次 acquire
```

### 9.2 资源释放

```text
任何 chat 退出路径都必须 release account
任何 stream 退出路径都必须 cancel transport
任何 session 创建成功后都必须存在清理责任
```

### 9.3 PoW target

```text
completion:
  /api/v0/chat/completion

upload:
  /api/v0/file/upload_file

edit_message:
  使用当前后端定义的对应 target
```

target 不能由 UI 或模型类型推断，必须由业务操作显式指定。

### 9.4 身份一致性

```text
device_id
smidV2
Cookie
UA
client platform
proxy
TLS profile
```

这些字段属于同一设备身份链，不能在不同请求路径中各自生成。

### 9.5 限流语义

```text
rate limited ≠ account busy
muted ≠ transient network failure
bad request ≠ provider failure
```

不能把所有错误交给统一重试器。

### 9.6 SSE 边界

SSE parser 必须支持：

```text
CRLF
LF
data 多行
事件跨 chunk
UTF-8 字符跨 chunk
[DONE]
尾随 usage
尾随 ds_title
尾随 ds_session_id
连接中断
```

### 9.7 配置真源

最终必须明确：

```text
App storage 是运行时真源
Native 库不持久化业务配置
Transport 不读取账号配置
PoW 库不读取账号配置
```

## 11. 最终验收标准

路线 C 完成后，应满足：

### 功能

- App 不再启动独立 `ds-free-api` 进程；
- 不再依赖固定本地端口；
- 不再使用 curl 文件轮询实现 SSE；
- 可以登录、切换账号、发送消息、取消消息；
- 支持多轮上下文；
- 支持图片/文件上传；
- 支持思考和搜索开关；
- 支持重试和编辑；
- 支持云端会话同步；
- 支持账号禁言、限流和恢复状态。

### 架构

- Transport 是纯 Native 库；
- Crypto 是纯算法库；
- PoW 是纯计算库；
- 业务状态全部在 JS；
- UI 不直接操纵 Native transport；
- Native 层不持有账号池；
- 没有 OpenAI/Anthropic 兼容服务器；
- 没有 Axum/admin/JWT 中间层。

### 稳定性

- App 页面退出不会留下后台请求；
- Native 库销毁前所有 stream 已停止；
- 账号不会因异常路径永久处于 busy；
- session 不会因异常路径大量泄漏；
- device_id 与 smidV2 不会漂移；
- 升级后不会出现旧进程占端口或旧 key 401；
- 网络断开后不会触发无界重试；
- QuickJS 主线程不执行阻塞网络或磁盘操作。

### 迁移安全

- 每个阶段可独立回滚；
- 阶段 0 之前不动旧业务；
- 阶段 1、2 可以用 mock server 和固定 PoW 样本验证；
- 阶段 3 才切换 App 默认调用路径；
- 最后才删除旧后端部署代码。

---

## 最终建议

采用路线 C，但实施顺序必须是：

```text
最小 JSAPI 验证
→ Transport Native 库
→ PoW Native 库
→ JS 账号池和 DeepSeek 业务
→ 真浏览器 device capture
→ 切换 App 默认路径
→ 删除旧进程后端
```

不要从 `completions.rs` 直接开始翻译，也不要先重写 TLS 或 PoW 算法。

**第一阶段成功的唯一标准不是“代码写出来”，而是确认：当前设备可以加载自定义 `libjsapi_*.so`，并且异步 Promise/事件回调与 QuickJS 生命周期可靠。** 这个结论决定后续路线 C 是否可以继续扩大。
